## 1. 프로젝트 개요

팀 캡스톤/과제용 전시회 프로젝트입니다. 관람객이 QR코드를 찍으면 휴대폰 화면에 가상(언리얼) 구급차 조작 환경이 뜨고, 고령자 집(모형)에서 낙상 신호가 발생하면 조작이 가능해집니다. 관람객이 가상 구급차를 조작하면 실물 RC카가 동일하게 움직이고, 목적지(고령자 집)에 도착하면 자율주행으로 원위치까지 복귀합니다.

### 전체 흐름 (5단계)

1. 위험 신호 발생 — 고령자 집 센서(시뮬레이션)가 낙상을 감지
2. 방문객 폰 알림 — 화면에 위험 신호 알림이 뜨고, 그 시점부터 구급차 조작 잠금이 해제됨
3. 가상+실물 동시 조작 — 관람객이 조작하는 가상 구급차 움직임이 MQTT를 통해 실물 RC카에 그대로 반영됨
4. 고령자 집 도착 — RC카가 목적지에 도달하면 화면에 알림이 뜨고 수동 조작 종료
5. 자율주행 복귀 — RC카가 스스로 원래 위치까지 돌아감

### 팀 구조 (역할 분담)

| 담당 | 역할 | 진행 상태 |
| --- | --- | --- |
| 개발 A (데이터) | `home_sim.py` — 고령자 집 낙상 감지 시뮬레이션, `home/alert` 발행 | 완료, 실제 하드웨어로 검증됨 |
| 개발 B (로버) | RC카 — `car/control` 구독해 실제 모터 구동, `car/telemetry`·`car/mode` 발행 | 완료, 실제 하드웨어로 검증됨 |
| 개발 C (언리얼) | 가상 구급차 조작 앱, QR 진입 | 미착수. 아키텍처 스펙은 확정되어 있음 (4절 참고) |

## 2. 하드웨어와 인프라 현황

- 라즈베리파이4(`raspi4`)에서 Mosquitto 브로커와 모든 Python 서비스가 돌아갑니다. 같은 Pi4에 `Digital_Twin`이라는 별개 프로젝트(이전 세션 작업물)도 공존하므로, GPIO 핀 사용이 겹치지 않도록 주의가 필요합니다.
- Pi4는 유동 IP를 쓰기 때문에 접속할 때마다 주소가 바뀔 수 있습니다. **mDNS 호스트명 `raspi4.local`**로 고정 접속할 수 있도록 avahi-daemon을 확인해 두었습니다. 다만 Windows PC에서 가끔 mDNS 해석이 실패하는 경우가 있으므로, 안 되면 Pi4에서 `hostname -I`로 IP를 직접 확인해야 합니다.
- Exhibit 관련 세 개의 Python 프로세스는 **systemd 서비스**로 등록되어 있어, 재부팅해도 자동으로 다시 시작됩니다.
  - `exhibit-home.service` → `home_sim.py`
  - `exhibit-car.service` → `car_subscriber.py`
  - `exhibit-dashboard.service` → `dashboard_server.py` (테스트용 대시보드, 포트 5050)
  - 같은 GPIO를 쓰는 `digital-twin-car.service`는 충돌을 막기 위해 **비활성화(disable)**해 두었습니다. 재부팅 이후 다시 활성화되어 있지는 않은지 확인이 필요합니다.
- `car_subscriber.py`는 `Digital_Twin` 프로젝트의 `motor_module.py`(`pi-rover/ch09_project` 버전)를 그대로 재사용하고, 파이썬 가상환경도 `~/Digital_Twin/venv`를 그대로 빌려 씁니다.

## 4. 아키텍처 핵심 결정 — "언리얼이 항상 주도, 실물은 항상 따라감"

이 프로젝트에서 가장 중요한 설계 결정입니다.

**배경**: 전시장 바닥에는 실제 차선이나 트랙이 없습니다. 도로는 언리얼 안의 가상 세계에만 존재합니다. 따라서 실물 RC카가 스스로 차선을 인식해서 자율주행하는 방식은 애초에 불가능합니다.

**결정한 방식**: 3단계(방문객 조작)와 5단계(자율주행 복귀) 모두, **언리얼이 항상 판단의 주체**가 되고 실물 RC카는 그 결과를 그대로 따라가기만 합니다.

- 3단계에서는 방문객이 언리얼 화면의 방향키를 눌러 가상 구급차를 조작하고, 그 입력이 `car/control`로 발행되어 실물에 그대로 반영됩니다.
- 5단계(자율주행 복귀)는 다음 방식으로 구현하기로 했습니다.
  1. 방문객이 조작하는 동안, 언리얼이 일정 간격(0.1~0.2초)으로 `(steering, throttle)` 명령을 배열에 기록합니다.
  2. 도착(`car/mode: arrived`) 신호를 받으면, 기록된 배열을 **뒤집고 부호를 반전**(`steering *= -1`, `throttle *= -1`)해서 같은 간격으로 재생합니다. 이렇게 하면 "왔던 길을 거꾸로" 가는 동작이 재현됩니다.
  3. 재생하는 동안에도 계속 `car/control`을 발행하므로, 실물 RC카는 평소와 똑같은 방식으로 이를 따라갑니다.
  4. 재생이 끝나면 `test/trigger/home`을 발행해 실물에게 복귀 완료를 알립니다(지금은 임시 토픽이며, 나중에 정식 토픽으로 교체할 필요가 있습니다).

이 방식은 Transform(좌표) 기반 경로 추종보다 구현이 훨씬 단순하고, 이미 만들어 둔 `car/control` 발행 구조를 그대로 재사용할 수 있다는 장점이 있습니다.

### 언리얼 화면 구상 (UI/UX)

- 고정된 탑다운(위에서 내려다보는) 3인칭 카메라를 사용하고, `SpringArmComponent`로 구급차에 부착합니다. 카메라는 회전하지 않으며, 구급차가 화면 중앙 하단에 오도록 배치합니다.
- `home/alert` 수신 시 화면 중앙에 빨간 배경의 "위험 신호 발생" 배너를 띄웁니다.
- `car/mode: arrived` 수신 시 배너를 초록 배경의 "위험 해제" 알림으로 전환한 뒤, 잠시 후 자동으로 사라지게 합니다.
- 화면 우측 하단에 방향키(D-pad) 위젯을 배치합니다. `home/alert`를 받기 전까지는 숨김 또는 비활성 상태이고, 받으면 활성화되며, `car/mode: arrived` 이후에는 다시 비활성화합니다.

### 언리얼이 구현해야 할 것 (정리)

1. 위험/해제 배너 UI
2. 우측 하단 방향키(D-pad) 위젯, 활성/비활성 전환
3. 방문객 조작 명령 기록과 역순 재생 로직
4. 역재생 완료 시 `test/trigger/home` 발행 (추후 정식 토픽으로 교체)

## 5. MQTT 토픽 설계

브로커는 Pi4의 Mosquitto(`localhost`, paho-mqtt 2.x)입니다.

| 토픽 | 발행자 | 구독자 | 발행 방식 | 설명 |
| --- | --- | --- | --- | --- |
| `home/alert` | `home_sim.py` | 언리얼, RC카(테스트용) | 낙상 감지 시 1회만 | `{"type": "risk_start"}` — 이벤트 전용, 상태 전환 시 딱 1번 발행 |
| `car/control` | 언리얼(방문객 조작이든 자율주행 재생이든 동일 채널) | RC카 | 조작 중 계속 | `{"steering": -1~1, "throttle": -1~1}` — MANUAL과 AUTONOMOUS 두 상태 모두에서 수신해 반영 |
| `car/telemetry` | RC카 | 언리얼 | 초당 2회 | `{"status": ..., "mode": ...}` — 위치 센서가 없어 상태값만 발행 중 |
| `car/mode` | RC카 | 언리얼, 화면 UI | 상태 전환 시 1회씩 | `{"mode": "arrived" \| "autonomous"}` |
| `test/trigger/fall` | 테스트 대시보드 | `home_sim.py` | 버튼 클릭 시 | 사람이 직접 누르는 테스트 트리거라, 이전 상태와 무관하게 항상 강제 발행(`force=True`)합니다. |
| `test/trigger/arrival` | 테스트 대시보드 | `car_subscriber.py` | 버튼 클릭 시 | MANUAL → ARRIVED → AUTONOMOUS 전환 트리거. 실제로는 초음파 등 센서로 교체 예정입니다. |
| `test/trigger/home` | 테스트 대시보드 | `car_subscriber.py` | 버튼 클릭 시 | AUTONOMOUS → MANUAL 리셋 트리거. 실제로는 언리얼의 "가상 원위치 도착" 신호로 교체 예정입니다. |

**중요한 미해결 리스크**: 과제 원본 PDF의 합격 기준에는 "home/vitals가 1초마다 흐른다"는 항목이 명시되어 있었는데, 팀 논의로 이 주기적 스트림을 없애고 `home/alert` 이벤트 하나로 단순화했습니다. 이 변경이 채점 기준에 영향이 없는지 담당 교수 또는 조교의 확인이 아직 이루어지지 않았습니다.

## 6. 테스트 대시보드 — "Rescue Relay Console"

언리얼이 아직 없는 상태에서도 전체 흐름(5단계)을 시험할 수 있도록 만든 웹 대시보드입니다. Pi4에서 평문 HTTP로 직접 서빙됩니다.

- 접속 주소: `http://raspi4.local:5050` 또는 `http://<Pi4 IP>:5050`
- 처음에는 Claude 아티팩트(HTTPS)로 만들었지만, `ws://`가 mixed-content로 차단되고 자체 서명 인증서의 `wss://`도 Mosquitto가 일반 GET 요청에 응답하지 않아 브라우저의 인증서 수락 화면 자체가 뜨지 않는 문제가 있었습니다. 그래서 **Pi4에서 직접 평문 HTTP로 서빙하는 방식으로 전환**했고, 이것이 정답이었습니다.
- 기능: 5단계 파이프라인 진행 상태 시각화, MQTT 실시간 로그, 낙상·도착·복귀완료 테스트 트리거 버튼, 방문객용 D-pad(조작 잠금과 연동).
- 관련 파일: `dashboard.html`, `dashboard_server.py`

## 7. RC카 조작 세부 사항

- 기본 속도(`SPEED`)는 여러 번 조정되었고, 가장 최근 값은 `0.3`입니다.
- 좌우 회전은 제자리 회전이 아니라 **자연스러운 커브 회전**으로 구현했습니다(`motor.move_curve_left` / `move_curve_right`, `inner_ratio=0.6`). 안쪽 바퀴 속도를 `SPEED × inner_ratio`로 줄이는 방식입니다.
- `car/control`의 `steering`/`throttle` 값은 현재 4방향 이산 동작(forward / backward / left / right / stop)으로 매핑되어 있으며, 연속적인(continuous) 제어는 아직 구현되어 있지 않습니다.

## 8. 해결된 버그와 교훈

- **SSH로 백그라운드 프로세스를 시작할 때, `pkill -f`와 `setsid ... &`를 같은 명령 안에 함께 넣으면 안 됩니다.** `pkill`의 검색 패턴이 그 명령 자신의 텍스트(뒤에 나오는 `setsid` 대상 스크립트 이름)에 걸려, 의도치 않게 자기 자신(부모 쉘)을 죽여버리는 문제가 있었습니다. `pkill`과 `setsid` 시작은 반드시 별도의 SSH 호출로 분리해야 합니다.
- **대시보드에서 `disabled` 속성이 걸린 버튼에도 브라우저가 `pointerdown` 이벤트를 전달하는 경우가 있습니다.** CSS만으로는 클릭 자체를 막을 수 없으므로, JavaScript에서 `btn.disabled` 여부를 직접 확인하는 코드가 필요했습니다.
- **"정확히 1회만 발행"하는 래치 로직은 사람이 직접 누르는 테스트 버튼에는 적합하지 않습니다.** 실제 센서라면 같은 사건을 중복 발행하지 않는 게 맞지만, 테스트 버튼은 누를 때마다 새로운 사건으로 취급해 항상 반응해야 합니다(`force=True` 패턴으로 해결).

2. **디자인 D, E 진행 상황 확인** — 다른 팀원 담당이라 진행 상황이 파악되지 않은 상태입니다. 특히 디자인 E(방문객 화면 UI)와 언리얼 쪽 작업 범위가 겹치지 않는지 역할 조율이 필요해 보입니다.
3. **테스트 토픽을 정식 토픽으로 교체** — `test/trigger/arrival`, `test/trigger/home`은 임시 토픽입니다. 실제 센서(도착 감지)와 언리얼(복귀 완료 신호)이 준비되면 교체가 필요합니다.
4. **합격 기준 미해결 리스크 확인** — 5절에서 언급한 `home/vitals` 관련 사항을 교수 또는 조교에게 확인해야 합니다.
